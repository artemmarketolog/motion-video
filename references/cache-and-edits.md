# Кэш и правки без полного перерендера

## Как это устроено

1. **Отпечатки кадров** (`scripts/probe.mjs`, через `hf.py probe`). Страница в песочнице перематывается
   на каждый кадр, для видимых элементов хешируются инлайн-стили (их пишет GSAP), SVG-атрибуты, геометрия,
   текст, стили из CSS (снятые без инлайна), байты картинок и шрифтов, время видео, пиксели canvas.
   Без скриншотов: весь ролик 12,6 с (378 кадров, 428 элементов) за ~5 с. Повторный прогон даёт те же хеши.
2. **Куски**: по `segment_seconds` (2 с) от каждого якоря из `video-spec.json` (`anchors`: начала сцен/склеек).
   Ключ куска = хеш его отпечатков + настроек рендера (версия HyperFrames, размер, fps, качество).
   Ключ не зависит от абсолютного времени: сцена, сдвинутая правкой раньше, берётся из кэша.
3. **Рендер только грязных**: соседние грязные куски одной сцены рендерятся одним запуском HyperFrames
   (`scripts/segment.py` делает композицию отрезка [f0, f1): таймлайн оборачивается в
   `tweenFromTo(t0, t1, {duration})`, тайм-атрибуты сдвигаются, `<audio>` убирается). Формат HLS:
   фиксированный GOP, каждый кусок начинается с ключевого кадра.
4. **Склейка** `-c copy` всех кусков → беззвучное видео; **микс** из `mix.json` (кэш) → mux с копией видеопотока.
5. Кэш в `<ролик>/.cache/` (`segments/*.ts`, `video/`, `audio/`, `probe/`, `logs/`, `stats.json`, `encode.json`).
   Каждый файл сверяется по sha256 перед использованием; лок сборки не даёт двум агентам собирать один ролик.
   Хранится 2 суток, если поставить `scripts/cache_gc.sh` в cron (README): он стирает `segments/`, `video/`, `audio/`, `probe/`
   у роликов, где 2 суток ничего не менялось. Правка такого ролика — полный рендер.
6. **Не больше 2 рендеров на машине** держит сам `mv.py build` (глобальный семафор на 2 слота в
   `~/.cache/motion-video/render-slots/`): третья сборка пишет `waiting for a render slot …` и стартует сама,
   когда слот освободится. Ручной `flock` больше не нужен; старые команды с `flock` работают как раньше.
   Слот держится только на время рендера кусков; probe, склейка и микс идут без очереди.

Точность: кусок против полного рендера 48,7 dB PSNR — столько же, сколько повторное кодирование тех же
кадров (48,0 dB); стыки покадрово не видны (`mv.py seams`). Разные воркеры дают ±1 уровень пикселя
(так и в самом HyperFrames), это ниже шума кодека.

## Типы правок и время (замеры 30.09.2026, сервер 6 ядер, 11 ГБ, software GPU)

| Правка | Что пересобирается | Замер / цель |
|---|---|---|
| громкость музыки/голоса/SFX, другой трек, carve | микс + mux | 6–8 с (цель ≤ 1 мин) |
| текст/цвет/картинка в одной сцене презентации 16:9 | куски этой сцены | 54 с за сцену 5,5 с (цель ≤ 3 мин) |
| текст в середине премиум-ролика 9:16 (05) | 1 кусок 2 с | 63 с (цель ≤ 6 мин) |
| сцена стала длиннее/короче (сценовый режим) | только она | 2 мин за сцену 6,5 с; остальные из кэша |
| сдвиг времени в непрерывном ролике (один дубль камеры) | хвост от точки правки | доля полного рендера; сначала попробуй поглотить паузой |
| слово в голосе той же длины | TTS фразы + микс (+ куски с этим текстом) | ~1–2 мин |
| глобальный стиль, шрифт, формат, fps | всё | полный рендер, называй честно |

Первая сборка: 05 (премиум, 12,6 с) ~7 мин против 11 мин прежним способом; презентация 23 с ~3,5 мин.

## Скорость рендера (замеры)

Куда уходит время (лог `.cache/logs/render-*.log`, кусок 120 кадров бумажной сцены 07, 3 воркера):
старт ~9 с, захват кадров скриншотами в программном Chrome ~80 с, кодирование ~37 с. Захват ускорить
нельзя без GPU; кодирование с 01.10.2026 идёт одновременно с захватом (`HF_DE_PARALLEL_STREAM` в `hf.py`)
и быстрее (x264 medium ~14 Мбит/с вместо slow CRF 15):

| Тот же кусок 07 (5 с, 1080×1920) | Время | Размер |
|---|---|---|
| было: delivery (slow, CRF 15), захват, потом кодирование | 136 с | 40 МБ (64 Мбит/с) |
| поток во время захвата, тот же кодек | 110 с | 40 МБ |
| стало: поток + medium ~14 Мбит/с | 86 с (−37 %) | 11 МБ (17 Мбит/с) |
| весь ролик 10 (25 с, 750 кадров) | 389 → 259 с | 114 → 47 МБ |

| Кусок 60 кадров 05 (тяжёлый: blur, DOF, blend) | Время |
|---|---|
| 1 воркер | 62 с |
| 2 воркера | 46 с |
| 3 воркера | 29–41 с (по умолчанию) |
| 4–5 воркеров | 40–42 с (хуже: упирается в 6 ядер) |

Дорогие эффекты (полноэкранный blur, копия слоя для DOF, blend-режимы) замедляют рендер в 5–8 раз.
Если сцене нужен дорогой эффект, сначала проверь её отдельно (`mv.py build` отрендерит только её).
Черновик: `mv.py build --draft` (15 fps, быстрый кодек, свои ключи кэша; финал не трогает).

## Правила, без которых кэш не работает

- Кадр — чистая функция времени (контракт HyperFrames): без `Math.random`, `Date`, таймеров, `onUpdate`
  с побочными эффектами, без измерения DOM в колбэках.
- Сцены в локальном времени (`start + dt`) и `c.scene(start)`; зерно в mvlib перезапускается на каждом якоре.
- Никаких величин от общей длины ролика (прогресс-бар на весь ролик, `steps(total)` на всё видео).
- Всё, что есть в кадре, — в DOM/CSS/файлах папки. WebGL-canvas без `preserveDrawingBuffer` помечай
  `data-mv-volatile` (такие кадры всегда перерисовываются).
- Если `mv.py plan` показывает больше грязных кусков, чем ожидалось, ищи глобальную причину до рендера.
- Якорь сцены на кадр позже границы двухсекундного куска даёт кусок в 1 кадр. С 01.10.2026 склейка
  задаёт длительность каждого куска явно, метки времени не съезжают (раньше падал `qa.py` по fps).

## Цикл правки

1. Найти ролик и его `edits.jsonl` (журнал: запрос, что поменяли, ревизия, что перерендерено, время).
2. Назвать тип правки и время по таблице.
3. Правка в исходнике → `python3 build.py` → `mv.py plan`.
4. `mv.py build -o output/master-rN.mp4 --note "..."` (или `mv.py audio` для звука).
5. `qa.py`, `mv.py seams`, `frames.py` на правленом месте, `audiocheck.py` если трогали звук.
   Полный художественный проход по нетронутым сценам не повторяется.
6. Ответ: ссылка, одна строка «что изменено», время.
